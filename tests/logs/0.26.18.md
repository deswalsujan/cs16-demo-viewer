## The change

- `src/ui/loop.js`, `frame`: `requestAnimationFrame(frame)` first, then each part through `framePart`, which catches an error and hands it to `frameError`: the playback step, the kill flashes and sounds, the radar following the picked player, `updateFeed`, `draw` (2D), `drawPlayhead`, `updateCentre`, the 3D view (`build3d` and `update3`), `updateHud`. `prevT = T` and the flashes' clean-up stay outside, so a failing sound or flash step can't make kills land twice. With no errors, the parts run in the same order as before.
- Each part on its own, where the decision's words were "the rest of the frame inside try/catch": with one try/catch around the whole rest, an error repeated every frame in, say, `updateFeed` would skip the radar, the timeline, the 3D view and the HUD every frame, which is the freeze the decision is about, with playback and sound running under it. For Sujan to approve in the pull request.
- `src/ui/debug.js`, `frameError`: a set of the messages seen in this page; a new one goes into `ERRLOG` as "<message> (caught in the frame loop, <first stack place with a line number, without the page's address>)", the 20-entry limit as before, and `console.error`; the first one in the page calls `toast()` with the approved words (9 s, its default). A message seen before does nothing. `update3` already restores `T` in a `finally`, so an error in the 3D view leaves playback time right.

## Before the merge: two fixes (Sujan, 7 Nov 2026)

Sujan approved a try/catch per part of the frame and asked for two fixes in this pull request, "both caused by the loop now running on after an error": "1. build3d() sets view3.map only on its last line, so a build that throws partway is now retried every frame (a full map rebuild about 60 times a second). - `src/view3d.part.js`, `build3d`: the build itself moved into `build3dNow`. `build3d` returns at once for a map marked failed (`view3.failed`, the `MAP` object), and on an error it clears what was half built (`clear3d`), marks the map, shows "<map> couldn't be drawn in 3D. The 2D view still works. Press ? and click Copy debug info to report it." with `status3`, and throws on, so the frame loop records the error (`frameError`) or, from `loadMap`, the promise rejects as before. `resetForNewDemo` clears the mark and the message; a new map is a new `MAP`, so the mark doesn't carry over. `src/ui/loop.js` doesn't call `build3d` for a failed map either.
- `src/view3d.part.js`, `update3Now`: after `clearRect`, `globalAlpha = 1` and `textAlign = 'center'` as asked, and also `textBaseline = 'alphabetic'` and `globalCompositeOperation = 'source-over'`: `drawPovHud` sets `'lighter'` and an alpha of 0.8 inside `save` and `restore`, and `drawSpecBars` a `textBaseline`, so an error between the two would leave those too. In a frame with no error these are the values the drawing already starts with (every text drawn sets its own `textAlign`; a normal frame ends on `'center'`), so nothing changes there.
- Not changed: an error between `save()` and `restore()` leaves one extra saved state on the canvas's stack each time; what's drawn is set right by the resets above and the `setTransform` already there, so only the stack grows, while that error repeats.
